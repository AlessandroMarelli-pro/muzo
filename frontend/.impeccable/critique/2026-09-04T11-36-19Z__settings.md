## Design Specificity Verdict

**LLM (unanchored):** Category-interchangeable settings boilerplate wearing the theme's paint. Swap the tokens and this is a Vercel/Supabase/Railway settings page — three stacked bordered rectangles, header row `h2` + muted `<p>`, `space-y` fields, small primary button bottom-left. Nothing says "crate room", "printed sleeve", or "music". DESIGN.md's central thesis — spot blue as a FIELD, not an accent — appears only as small filled buttons; never as an organizing surface. Shadows aren't applied (`rounded-lg border` with no `shadow-sm`), a direct hit on "never a hard-edged panel" + the Ghost Border Rule. Off-scale `text-lg font-semibold` headers; raw `rounded-lg` (should be `rounded-xl`); raw amber Tailwind for the scan banner despite a purpose-built `warning-surface/-border/-foreground` token trio. Competent and shippable; not authored.

**Deterministic scan:** `detect.mjs --json` on all 4 source files → exit 0, `[]` (zero findings). Caveat from Assessment B: for `.tsx` inputs only the regex text engine runs (Tailwind class patterns, CSS-in-JS blocks, Google fonts, em-dash floor, source design-system checks) — page-level analyzers (layout, DOM contrast, focus rings, tab order) do NOT run on source files. A deliberately-bad control snippet (`style={{color:"#ff0000"}}` + no-op onClick) also returned `[]`, confirming inline React style objects / JSX-prop hex are outside this invocation's scope. So `[]` = "clean against the regex subset", not "fully audited". No false positives (no findings). Files correctly use ASCII `--` not em-dashes.

**Visual overlays:** Not available. The dev route `/settings` redirects unauthenticated users to `/login` (better-auth session; no dev bypass, no mock-auth flag). Neither assessment could authenticate (prohibited). No live Settings render, no overlay injection, no live-server flow. Assessment A built a token-accurate static reconstruction from source and captured desktop (1440w) + mobile (390w) — faithful for layout/spacing/hierarchy/rounding/missing-shadow; does not exercise live data, skeletons, real toasts, the ProviderAuthDialog, or the scan-in-progress banner (those evaluated from code). Fallback signal: static source read + design review only for live a11y/visual specifics.

## Overall Impression

A working configuration form a developer can complete, built without reference to the design system's actual rules. The IA is the deepest problem: four responsibilities (engine mode, engine scaling, third-party enrichment keys, backend OAuth credentials, streaming account connections) split across three cards on boundaries that make sense to the backend, not the user. The `AiServiceSettings` component alone is ~230 lines doing four jobs. A new self-hoster lands here with everything empty, every badge red, and no path — no "start here", no required-vs-optional, no minimal-viable-config.

Biggest opportunity: restructure the IA by user task and re-author against DESIGN.md — a two-pane settings shell that matches the app's existing rail+inset DNA.

## What's Working

1. **Secret-handling mechanism** — never echoes stored secrets, only sends touched fields, clears inputs after save, and the "leave blank to keep current" hint appears only when a value is stored AND the field is untouched. Right mechanism; needs a clearer visual.
2. **Contextual help density** — every field has a one-line purpose ("Album art lookup", "LLM filename cleaning"), console deep-links, callback-URI helper block. The best part of the page.
3. **Status-aware disabling** — the scan-in-progress lockout on mode/replica controls disables *before* the user hits a rejection, with an explanation. Good defensive behavior (styling of the banner is wrong).

## Priority Issues

### [P0] IA: card boundaries don't match user intent
- **Why:** First-run users can't form a mental model — keys for one conceptual thing (e.g. "playlist sync from Spotify") are split across cards; analysis keys live in both card 1 and card 2 (cosine.club). They miss keys, don't know what's required, bounce between cards.
- **Fix:** Regroup by task: (1) Analysis engine — mode/endpoint/replicas + the enrichment keys it uses, with "required to analyze" / "optional, improves results" split; (2) Streaming & playlist sync — OAuth app credentials AND the resulting account connections co-located per provider; (3) cosine.club as its own block. Consider a tabbed / left-nav settings shell instead of one 2xl scroll column.
- **Command:** `$impeccable shape` (IA restructure) then `$impeccable` redesign

### [P1] Design-system violations throughout
- **Why:** DESIGN.md exists to keep every surface one authored world; these components read as a different app, and `theme:check` won't catch component-level drift.
- **Fix:** Rebuild on `Card`/`CardHeader`/`CardTitle` primitives (`rounded-xl` + `shadow-sm` + `py-6`), map the amber banner to `warning` tokens, replace `window.confirm()` with the themed dialog, separate sub-sections by tone not hairlines.
- **Command:** `$impeccable polish` / `$impeccable colorize` (warning tokens, field-blue)

### [P1] No dirty-state, no unsaved-changes guard, toast-only errors
- **Why:** Secrets are high-stakes, low-feedback input. Losing a pasted API key with no warning is the worst thing a settings page can do; a failed save looks identical to a success once the toast fades.
- **Fix:** Per-card dirty indicator (save button ghost → filled-blue when dirty — a legit Field-Rule use), route-leave guard when any field is dirty, inline per-field error text.
- **Command:** `$impeccable harden`

### [P2] First-run experience teaches nothing
- **Why:** PRODUCT.md says this is where a new Docker user wires up the whole app; right now it's a pile of empty fields with no priority, and `mode` defaults to `remote` (the non-default first move for a self-hoster is `local`).
- **Fix:** Top-of-page "Getting started" state when nothing is configured — 3 numbered steps (pick analysis mode → add the one key you need → optionally connect streaming). Default `mode` to `local`. Mark genuinely-required fields distinctly.
- **Command:** `$impeccable onboard`

### [P2] `AiServiceSettings` is monolithic (4 jobs, ~230 lines)
- **Why:** Cognitive overload; the "Apply to running container" vs "Save API keys" distinction (recreate-container vs save-to-disk) is a subtle idea drowned in same-size text.
- **Fix:** Split into "Engine" (mode + endpoint/replicas) and "Enrichment keys" (the 5 keys), with save-vs-apply as one primary Save + a contextual "…and reload the running container now?" follow-up, not two peer buttons.
- **Command:** `$impeccable distill`

## Minor Observations

- `USER_ID = 'default'` hardcoded in `account-connections.tsx:14` — connections not actually user-scoped despite the auth system (likely fine for local-first single-user; worth a comment/assertion).
- Health badge uses `variant="outline"` for "Unavailable" — arguably a `warning` state, not neutral.
- `CircleDashed` used for both "Unavailable" and "Not connected" — two meanings, one icon.
- Callback-URI block (`API_BASE_URL`) has no copy button — users will mis-transcribe into three consoles.
- Mobile 390w: AI Service header badge wraps so the icon sits above its label (header `justify-between` flex row, no `shrink-0` / wrap handling).
- `text-base` inputs on mobile → `text-sm` on md is correct per DESIGN.md.
- Muddy heading outline: API-keys `<h3>` inside a card whose title is `<h2>`, with an intervening non-heading Mode/Endpoint block.
- Toast-only success = no audit trail; a user who configured 8 keys has no persistent confirmation beyond bullet placeholders.

### A11y (Assessment B, static from source)
- `window.confirm` for destructive disconnect — `account-connections.tsx:114`; inconsistent with the Radix `ProviderAuthDialog` in the same file. Use `AlertDialog`.
- Toast-only error surfacing across all mutations (`ai-service-settings.tsx` :66/69/86/90/98/104/128/131/141/145; `integration-settings.tsx` :44/48; `account-connections.tsx` many) — Sonner toasts are `role="status"` polite, auto-dismiss, not tied to the failed field.
- No `<form>` element / form landmark in any of the three panels — no implicit submit (Enter does nothing), no `aria-labelledby` to the `<h2>`/`<h3>`. Panels could be `<section aria-labelledby>`.
- Section headings not programmatically linked to their regions (no `aria-labelledby` / `role="region"` / `<section>`).
- `ToggleGroup` mode selector has `aria-label` (good) but a separate inert visible `<Label>Mode</Label>` at `ai-service-settings.tsx:184` with no `htmlFor` / matching `id`.
- Number input silent clamping (`Math.max(1, …)`) with no `aria-describedby` to the two helper paragraphs; same missing `aria-describedby` for every `<Input>` with an adjacent hint.
- Disabled controls during `scanInProgress` have no AT-visible reason; the amber banner is a plain `<p>`, not `role="status"` / `aria-live`, not linked via `aria-describedby`.
- Focus rings present in `input.tsx` / `button.tsx` source (`focus-visible:ring-1 ring-ring`) — unverified live.
- Client IDs correctly `type="text"`, secrets `type="password"`, all keyed inputs `autoComplete="off"` — good.

## Questions to Consider

- What if Settings were a two-pane shell (left sub-nav on the `sidebar` surface, content on stock) mirroring the app's rail+inset DNA, instead of one 2xl scroll column?
- What if the enrichment keys were presented as a checklist of *capabilities* ("Album art", "Filename cleaning", "Genre/label data") each showing which key powers it and whether it's set — configuring outcomes, not credentials?
- What if each streaming provider were one block owning both its OAuth app credentials and its account connection + connect/disconnect action, with the callback URI + a copy button right there?
- Where can "crate room" personality land without gimmickry? Likely the first-run / empty state — framed as setting up your rig before a dig: sparse, confident, one blue call-to-action.

## Redesign verdict

**Yes, warranted** — "redesign" = restructure the IA + re-author against the design system, not restyle. There's no Muzo-specific thinking to preserve, only the inline-help copy and the secret-handling mechanism.

Sketch: two-pane settings shell (left sub-nav Analysis · Streaming · Discovery · Account on `sidebar` surface, content on stock; mobile → accordion or top segmented control). **Analysis** is the hero of Settings for a local-first product: an engine panel (Local vs Remote as a real choice with consequence text, then only that mode's fields) + an Enrichment checklist-of-capabilities. **Streaming**: one block per provider owning OAuth creds + connection state + action, callback URI + copy button inline. **Discovery**: cosine.club alone. Real `Card` primitives, spot blue as a field for the active sub-nav item and the dirty/primary save state, status via `success`/`warning`/`info` chip tokens with icon+label. First-run state sequencing the three sections.
